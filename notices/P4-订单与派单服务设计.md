# P4 订单与派单服务 — 设计与实施

> 阶段：第四阶段（P4）。在 P3 客户数据（微信登录 + 昵称头像）完成后，进入订单履约链路。
> 本文固化 2026-10-08 与用户确认的设计决策，作为实现依据。

## 1. 设计决策（已确认）

| 设计点 | 决策 |
| --- | --- |
| 陪玩入驻 | 小程序「我要加入」提交申请 → 管理员审核 → 通过后后台建陪玩档案（绑游戏分区 + 接单开关） |
| 派单模式 | 人工指定 + 陪玩确认（可接受 / 拒绝，拒绝回到待派单可换人） |
| 预约时段 | 下单时选「预约日期 + 三档时段（上午/下午/晚上）」 |
| 状态机 | 完整履约闭环（见下） |
| 边界 | 不做抢单大厅、不做真实支付、不做真实提现；售后/退款留给 P5 |

## 2. 数据模型

### 2.1 Partner（陪玩档案）
由管理员在后台创建（对应已通过审核的用户）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| user | FK → User（OneToOne） | 陪玩对应的账号（须已通过申请审核） |
| game | FK → GamePartition | 绑定的游戏分区 |
| is_active | Bool | 接单开关（关闭后不再接收新派单） |
| intro | CharField | 陪玩简介（可选） |
| version | Int | 乐观锁版本 |
| created_at / updated_at | | |

约束：`unique(user)`——一个账号一个陪玩档案；`unique(user, game)` 允许同账号在不同游戏分区各有一个档案（MVP 先按单分区实现，保留扩展）。

### 2.2 PartnerApplication（入驻申请）
由用户在「我要加入」页提交。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| user | FK → User | 申请人 |
| game | FK → GamePartition | 意向游戏分区 |
| reason | TextField | 申请说明（自我介绍/擅长等） |
| status | choices | PENDING / APPROVED / REJECTED |
| reviewed_by | FK → User（可空） | 审核人 |
| reviewed_at | DateTime（可空） | 审核时间 |
| created_at | | |

约束：同一用户对同一游戏只能有一条非终态的申请（unique 约束 `(user, game)`，MVP 简化）。

### 2.3 订单扩展

`Order` 新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| appointment_date | DateField（可空） | 预约日期 |
| appointment_slot | CharField（可空） | 时段：`morning`/`afternoon`/`evening` |
| partner | FK → Partner（可空） | 派单的陪玩 |

`Order.Status` 扩展为：

```
PENDING_PAYMENT      待付款
PENDING_ARRANGEMENT  待派单（已付款）
PENDING_ACCEPTANCE   待陪玩确认
ACCEPTED             已接单（待服务）
IN_SERVICE           服务中
PENDING_CONFIRMATION 待客户验收
COMPLETED            已完成
CANCELLED            已取消
```

状态机流转：

```
PENDING_PAYMENT ──付款──▶ PENDING_ARRANGEMENT
PENDING_ARRANGEMENT ──派单──▶ PENDING_ACCEPTANCE
PENDING_ACCEPTANCE ──陪玩接受──▶ ACCEPTED
PENDING_ACCEPTANCE ──陪玩拒绝──▶ PENDING_ARRANGEMENT（可换人重派）
ACCEPTED ──开始服务──▶ IN_SERVICE
IN_SERVICE ──完成──▶ PENDING_CONFIRMATION
PENDING_CONFIRMATION ──客户验收──▶ COMPLETED
（任意非终态在业务允许时 ──取消──▶ CANCELLED，沿用现有取消规则）
```

## 3. API 契约

### 3.1 小程序端（Bearer）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/me/partner-application/` | 提交入驻申请（game, reason） |
| GET | `/me/partner-application/` | 查询我的申请状态 |
| POST | `/me/orders/{id}/confirm/` | 客户验收订单（IN_SERVICE → PENDING_CONFIRMATION 之后） |
| GET | `/me/partner/orders/` | 陪玩工作台：派给我的订单 |
| POST | `/me/partner/orders/{id}/accept/` | 陪玩接受派单 |
| POST | `/me/partner/orders/{id}/reject/` | 陪玩拒绝派单 |
| POST | `/me/partner/orders/{id}/start/` | 开始服务 |
| POST | `/me/partner/orders/{id}/complete/` | 完成服务 |

下单 `POST /me/orders/` 扩展入参：`appointment_date`（YYYY-MM-DD）、`appointment_slot`（morning/afternoon/evening）。

### 3.2 管理端（Session + CSRF）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/management/partner-applications/` | 申请列表（可按 status 筛选） |
| POST | `/management/partner-applications/{id}/approve/` | 通过申请（自动建 Partner） |
| POST | `/management/partner-applications/{id}/reject/` | 驳回申请 |
| GET/POST/PATCH | `/management/partners/` | 陪玩档案列表 / 新增 / 编辑（绑分区、接单开关） |
| POST | `/management/orders/{id}/assign/` | 派单（指定 partner_id，含冲突检查） |

## 4. 关键规则

- **冲突检查**：派单时校验同一陪玩在「同一天 + 同时段」是否已有未完成的订单（非 CANCELLED/COMPLETED），有则返回 `PARTNER_CONFLICT`，运营需换人。
- **幂等 + 版本**：所有状态流转动作沿用现有 `Idempotency-Key` + `version` 乐观锁；每次流转写 `OrderStatusHistory`。
- **权限**：陪玩工作台接口校验 `request.user` 有对应 `Partner` 且 `is_active`；管理端动作校验 `is_staff`。
- **接单开关**：`Partner.is_active=False` 时，派单接口拒绝，陪玩工作台不接受新单。
