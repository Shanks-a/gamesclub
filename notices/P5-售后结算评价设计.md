# P5 售后、结算与评价 — 设计与实施

> 阶段：第五阶段（P5）。在 P4 订单与派单完成后，补完整订单履约链路的后半段（评价、售后、退款、陪玩结算），并补齐前端单测与 CI 体现工程严谨度。
> 本文固化 2026-10-13 与用户确认的设计决策（范围：评价 + 售后退款 + 陪玩结算三块全做；前端测试逻辑 + 组件一起；提交粒度四步）。
> **实施状态：已完成**（2026-10-13）。后端 70 项测试通过、双端 type-check 与单测全绿、已推送 main。

## 1. 设计决策（已确认）

| 设计点 | 决策 |
| --- | --- |
| 评价范围 | 仅订单完成后可评，一单一评（`Review` 对订单 OneToOne），1–5 星 + 可选文字 |
| 售后窗口 | 服务中 / 待验收期间始终可申请；完成后须在售后截止时间内（默认 48 小时，可配置） |
| 退款金额 | 整数分；可退金额 = 实收 − 已成功退款 − 处理中预留退款，超退拒绝 |
| 退款流程 | 申请 → 管理员复核（通过建**预留退款** / 驳回）→ 退款执行（成功 / 失败 / 未知），成功才更新累计退款 |
| 抽成 | 统一抽成比例（基点 `commission_bp`，10000=100%），下单时快照到订单；历史订单回填 20%（2000） |
| 结算口径 | 净收入 = 实收 − 已退款；抽成 `(net*bp+5000)//10000`（整数分四舍五入）；陪玩收益 = 净收入 − 抽成 |
| 结算资格 | 订单完成 + 过售后时限 + 无处理中售后 + 无处理中/未知退款 + 有陪玩 + 未结算 |
| 边界 | 不做真实支付 / 提现 / 自动追偿；结算后不做已结算订单的售后自动追偿 |

## 2. 数据模型（迁移 0008–0010）

### 2.1 Review（评价）— 0008
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| order | OneToOne → Order | 一单一评 |
| user | FK → User | 评价用户 |
| rating | PositiveSmallInt | 1–5 星 |
| content | TextField | 评价内容（≤2000 字，可选） |
| created_at | | |

### 2.2 Order 扩展字段（0008）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| commission_bp | PositiveInt | 下单时快照的抽成基点 |
| aftersale_deadline | DateTime（可空） | 售后截止时间（验收时写入 = completed_at + 窗口） |
| completed_at | DateTime（可空） | 完成时间 |
| refunded_amount_cents | PositiveInt | 累计已成功退款（分） |
| reserved_refund_cents | PositiveInt | 处理中预留退款（分） |

### 2.3 AfterSaleCase / Refund / Evidence（售后）— 0009
- **AfterSaleCase**：`order`（FK）、`user`、`case_no`（唯一）、`amount_cents`、`reason`、`status`（OPEN/APPROVED/REJECTED/CLOSED）、`resolution`、`reviewed_by/at`。约束：`one_open_aftersale_per_order`（每单同时最多一个 OPEN 案件）。
- **Refund**：`order`、`case`（可空）、`refund_no`（唯一）、`amount_cents`、`status`（PENDING/SUCCEEDED/FAILED/UNKNOWN）、`reason`、`reviewed_by/at`。约束：`one_pending_refund_per_order`（每单同时最多一个 PENDING 退款）。
- **Evidence**：`case`、`uploader`、`file_path`、`mime_type`、`size_bytes`（私有存储，先传后挂接）。

### 2.4 SystemConfig（系统配置）— 0009
`key`（唯一）+ `value_json`（JSON）+ `updated_by/at`。用于抽成比例、售后时限等全局配置；`get_config_int(key, default)` 读取并容错。

### 2.5 Settlement / SettlementItem（结算）— 0010
- **Settlement**：`batch_no`（唯一）、`executed_by`、`created_at`。
- **SettlementItem**：`settlement`、`order`（唯一）、`partner`、`paid_amount_cents`、`refunded_amount_cents`、`net_income_cents`、`commission_bp`、`commission_cents`、`partner_income_cents`、`created_at`。约束：`SettlementItem.order` unique（一单只能结算一次）。

## 3. 接口与关键实现

### 3.1 小程序端（Bearer 认证，均带 Idempotency-Key）
| 端点 | 方法 | 说明 |
| --- | --- | --- |
| `/api/v1/me/orders/<pk>/review/` | GET/POST | 查询 / 提交评价（COMPLETED 且未评） |
| `/api/v1/me/orders/<pk>/aftersale/` | GET/POST | 查询 / 申请售后（窗口内，可退金额校验） |
| `/api/v1/me/aftersale-evidence/` | POST | 上传售后图片凭证（私有存储，先不挂案件） |
| `/api/v1/me/orders/<pk>/confirm/` | POST | 验收时写 `completed_at` + `aftersale_deadline` |

### 3.2 管理端（Session + CSRF）
| 端点 | 方法 | 说明 |
| --- | --- | --- |
| `aftersales/`、`aftersales/<pk>/` | GET | 售后案件列表 / 详情 |
| `aftersales/<pk>/review/` | POST | 复核：approve（建 PENDING 退款 + 预留）/ reject |
| `refunds/<pk>/execute/` | POST | 退款执行：success / fail / unknown |
| `orders/<pk>/cancel-refund/` | POST | 已付款未开始取消全额退款 |
| `settlements/`、`settlements/<pk>/` | GET/POST | 结算批次列表 / 发起结算（`order_ids` 批量） |
| `settings/` | GET/PATCH | 读取 / 修改抽成与售后时限（PATCH 仅超管） |

### 3.3 并发与一致性
- 结算 `_settle_one` 在 `transaction.atomic()` + `select_for_update()` 内锁单校验：COMPLETED + PAID + 过售后时限 + 无 OPEN 案件 + 无 PENDING/UNKNOWN 退款 + 未结算 + 有陪玩。
- 抽成整数分计算：`commission = (net * commission_bp + 5000) // 10000`（四舍五入，禁止浮点）。
- 退款成功：`refunded += amount`、`reserved = max(0, reserved - amount)`；失败：释放预留；未知：保留预留阻止结算。

### 3.4 迁移回填
`0009` 用 `RunPython` 把历史订单 `commission_bp` 回填为 2000（20%），并创建默认 `SystemConfig` 条目（`commission_bp`、`aftersale_window_hours`）。

## 5. 质量提升（同一迭代）

- 订单列表 N+1 修复：`OrderSerializer.get_review` 改用 `prefetch_related('review')` 缓存，三个订单列表接口补 `select_related('product','partner','partner__user__profile')`；30 单序列化从 ~31 次查询降到 2 次。
- `requirements.txt` 锁精确版本（Django 5.2.17 等），CI / 本地一致。
- `settings.py` 补 DEBUG=False 生产安全基线（SSL 跳转 / 安全 Cookie / HSTS / 防嗅探 / X-Frame-Options）。
- 管理端 `customers` 精确异常替代裸 `except Exception`；小程序售后退款金额强制整数化。
