# 客服互通、订单同步与售后修复

更新日期：2026-10-16。以下描述当前本地实现；支付、退款和结算仍是模拟业务。

## 本次调整

1. 提交订单只保留上方「客服安排／指定陪陪」。指定按钮打开原有底部选择弹窗，选定后显示姓名；去掉重复入口。
2. 新增站内在线客服，用户、陪玩均可发文字消息，管理后台新增「客服会话」。订单管理提供「联系用户／联系陪玩」，订单对话也可直接带订单号联系客服。原微信／企业微信配置保留为额外渠道，不再阻挡站内沟通。
3. 后台订单、概览、售后等业务列表每 5 秒更新；页面不可见时暂停。编辑弹窗打开时不替换列表，只读订单详情仍自动更新。用户订单、会话列表和聊天页在显示时轮询，隐藏或退出时停止，保留输入草稿。
4. 订单会话和客服会话显示未读数量、待我回复／已回复等待对方。客服收件箱可筛选未读和待回复。客服读取只消除未读，发送回复才改变待回复标记。两名客服共用团队已读状态，不是各自独立未读。
5. 订单页付款成功后，页面返回按钮直接回首页，并拦截支持的平台返回事件；不会返回提交订单或支付步骤。微信端仍需真机验证系统手势及键盘行为。
6. 订单返回售后摘要、复核说明和退款状态。处理中、已通过、已关闭的售后均阻止再次申请；驳回后允许在原期限和剩余可退金额内重新申请。通过后的退款失败／未知需客服跟进，不能通过反复申请绕开。已通过但尚未妥善退款的案件阻止结算。
7. 后台售后列表及复核弹窗展示原始申请原因、金额和复核说明；仅待执行退款显示模拟结果操作。

## 履约规则与一致性（合并旧履约草稿）

主流程：`PENDING_PAYMENT → PENDING_ARRANGEMENT → ACCEPTED → IN_SERVICE → PENDING_CONFIRMATION → COMPLETED`。

- 客服在系统外协调抢单及通知；指定陪玩只是意向。后台assign要求version、partner_id及可选note，校验同游戏、账号／接单资格、自接单及已填写时段冲突；更换意向人选须说明。
- 客服确认时，在同一事务写实际陪玩、订单会话、状态历史、版本及审计；已存在会话的参与者不一致时拒绝覆盖。历史PENDING_ACCEPTANCE仍需客服确认，不静默迁移。
- 实际陪玩在订单对话开始服务，写started_at；申请完成写completion_requested_at及结构化完成申请消息。客户在会话或订单页同意后才写completed_at及售后截止时间，计入近30天和累计榜单。
- 陪玩start／complete要求version和Idempotency-Key，事务内统一写状态、时间、事件、历史及审计；重复请求回放，旧版本、越权、越级拒绝。普通文字不能伪造服务事件。
- 客服旧start／complete返回PARTNER_MANAGED_SERVICE 403；陪玩旧accept／reject停用。无自动验收、按购买时长自动结束或客服代客户确认。
- 0014_service_chat_progress迁移仅从已有历史回填时间，不补造消息或状态；0015新增客服会话。新环境启动前执行migrate。
- 商品单平台只显示该平台，双平台可切换；后端同样验证，不接受URL或客户端绕过商品配置。
- 聊天输入明确高度、外层留白，消息滚动区与输入栏分离，避免文字被裁切；仍需真机核验键盘及安全区。

### 多角色复验要点

使用固定账号和独立浏览器身份，完成普通下单与指定下单两条链路。客服确认后，陪玩从消息进入订单会话依次开始／申请完成；客户暂不同意时状态保持待确认、榜单不增，客户同意后完成并增加一次。反复提交不重复计数；无关用户、非实际陪玩和客服均不能代为推进服务。已有订单只由测试操作者决定是否验收，不在文档中指定必须处理某一条历史记录。

2026-10-15历史回归已覆盖平台校验、中文输入、服务时间顺序、重复／并发、跨用户隔离、事务回滚、事件伪造和榜单口径；临时联调单在客户同意后近30天及累计单量均增加一次，清理后恢复原数据。该轮127项测试已被下方2026-10-16全量136项回归覆盖。更早的客服代开始／完成方案已废止。

## 客服会话边界

- 每位咨询人、每张订单独立一个会话；无订单的一般咨询也可使用。用户与陪玩的客服会话互相不可见，普通用户不能调用管理端接口。
- 客服可看到共享收件箱，回复记录保留具体发送员工，客户端显示「客服」。现有用户与陪玩的订单私聊仍仅由双方访问，不因增加客服会话而开放给员工。
- 发送限制为 1～2000 字，空白消息拒绝；客户端保存重试标识，断网重试不会重复发送同一条消息。管理端沿用 Session + CSRF，用户端沿用 Bearer 登录校验。
- 当前支持文本与轮询同步，没有附件、语音、撤回、离线推送、坐席分配或 WebSocket。长会话分页、限流、消息保留策略属于后续规模化工作。
- 新迁移：`0015_support_conversations`，只新增客服会话／消息表，不修改已有订单。

## 需要审查的后端能力清单

此前所说“有些后端能力还没有完整页面”，具体如下，不等同于已接通真实资金渠道：

| 能力 | 现有实现 | 当前页面／缺口 |
| --- | --- | --- |
| 已付款但未开始服务的取消退款 | `POST management/orders/{id}/cancel-refund/`，限定待派单／历史待确认／已接单，模拟全额退款并取消订单 | 管理后台还没有专用取消退款按钮和确认说明；用户端已付款订单走客服沟通 |
| 未付款订单并发编辑 | 已付款禁止通用编辑／删除，写入使用事务 | 未付款订单的通用编辑／删除尚未校验请求版本，需补齐多客服同时编辑的冲突提示 |
| 售后图片凭证 | `POST me/aftersale-evidence/` 上传图片，申请时传 `evidence_ids`；案件查询包含凭证 | 用户申请表目前仅金额＋文字；客服缺凭证查看界面。默认媒体存储返回 URL，尚未形成带鉴权的私有下载链路，不应宣称已经安全私有化 |
| 退款结果异常处理 | `refund_execute` 可模拟成功／失败／未知；预留资金和结果已记录 | 失败后重试、未知后查单确认尚未完成；当前保留售后通过状态并阻止结算，不能把重新申请当作退款重试 |
| 结算计算与明细 | 选择内部订单 ID 后生成批次和每单应付陪玩金额；防重复结算 | 已有批次页面，但输入的是数据库数字 ID，并非 GC 订单号；仍缺便捷候选订单勾选、真实打款、打款结果和对账核销 |
| 陪玩订单读取 | `GET me/partner/orders/` | 没有独立陪玩工作台是用户主动取消的设计；实际陪玩通过订单会话开始服务、申请完成，不应恢复旧 accept/reject 入口 |
| 公开内容管理 | 用户发表动态／点赞／评论，作者可删除；Django 管理后台可隐藏违规内容 | 面向运营的举报队列、审核流程、反刷和媒体下架尚未补齐 |

## 结算批次有什么用

结算批次是一次“算账”的结果：将符合条件的订单汇总，保存每单实收、退款、净收入、平台抽成和陪玩应得金额。例如实收 100 元、已退 20 元、抽成 20%，平台 16 元、陪玩 64 元。重复加入同一订单不会重复结算。

只有已付款、已完成、过售后期限、有实际陪玩、没有待处理／已通过待退款售后、没有待退款／结果未知退款且未结算的订单才可入账。页面当前不会向任何账户转账；真实打款和对账需要另接。未开始使用财务结算时可以暂不操作这个页面。

## 业务与客服配置有什么用

| 配置 | 作用 | 修改何时生效 |
| --- | --- | --- |
| 抽成比例 | 以基点存储，2000 = 20%，10000 = 100% | 下单时写入订单快照，只影响后续新订单，不改老订单抽成 |
| 售后时限 | 默认客户确认完成后 48 小时；服务中／待验收仍可申请 | 确认完成时生成截止时间；已有截止时间不会被后续配置修改 |
| 外部客服渠道 | 可选微信小程序原生客服或企业微信，另有接待说明 | 保存后用户重新加载客服入口读取；关闭外部渠道仍可使用站内客服 |

普通测试客服可以查看这些配置，保存需超级管理员。客服接待本身在「客服会话」，不需要先填写外部客服账号。

## 人工复验顺序

1. 测试用户下单：提交页只出现一个指定入口；选择后显示姓名。模拟付款，再点返回，应回到首页；后台订单页不手动刷新，约 5 秒内进入待派单。
2. 用户订单→联系客服→进入在线客服：输入中文发送。后台客服会话出现未读与待回复；打开后仅未读消失，回复后变为已回复。用户停留在会话中应自动收到回复。
3. 客服在订单管理联系实际陪玩；切换固定陪玩账号查看「消息」，回复后客服自动收到。用户不能查看该陪玩的私有客服会话。
4. 订单会话继续按“客服分配→陪玩开始→陪玩申请完成→客户同意”推进；不改变主流程。
5. 用户申请售后，后台查看原因并驳回；用户订单自动显示驳回说明并恢复申请按钮。在原期限内重提后，客服通过：按钮应消失。
6. 对该模拟退款登记成功，用户订单显示「售后已通过 · 退款已完成」和已退款金额；刷新／重新登录后仍不出现申请按钮。失败／未知则显示明确状态，不能重新申请或结算。

本地人工验证仅使用既定七个测试账号；临时回归记录带 `QA-SUPPORT-20261016` 标记，验证后清理，不替用户处理其原有订单或售后。
